# screenwriter_app

Fadewright web app (slice F4 of `../screenwriter_plans/plans/2026-09-20-frontend-mvp.md`). Private repo, `private: true`, local-packages phase: no publishing, no version bumps, no CI workflow.

## Tech stack

Bun, Vite 7, React 19, TypeScript, Tailwind 3 (via `@sudobility/design`'s `createTailwindPreset()`), `react-router-dom` 7, `@tanstack/react-query` 5 (one `QueryClient`; the client library's hooks read it), zustand (used by the lib's stores), i18next + `react-i18next` (app-owned init, single `app` namespace), Vitest + jsdom + `fake-indexeddb`, Playwright (`@playwright/test`).

**@sudobility architecture, matching `../music_app`**: `@sudobility/building_blocks` (topbar/footer shell, `FormModal`), `@sudobility/components` (`Section`/`Card`/`Grid`/`Heading`/`Text`/`Button`/`Input`/`Dropdown`/`FormModal`/`LanguageValidator`/`LanguageRedirect`/`ProtectedRoute`), `@sudobility/design` (Tailwind preset + theme tokens), `@sudobility/auth-components` (presentational `Avatar` only — not its own Firebase-config-driven `AuthProvider`, see Auth below). `building_blocks`' single bundled `dist` pulls in its full peer graph unconditionally (not just the symbols used), so `package.json` also carries `@sudobility/auth_lib`, `@sudobility/di`, `@sudobility/di_web`, `@sudobility/entity_client`, `@sudobility/types`, `firebase`, `i18next-http-backend`/`i18next-browser-languagedetector`, `react-helmet-async`, `class-variance-authority`, `clsx`, `tailwind-merge`, `@heroicons/react` — most unused directly, needed only so `vite build`/`tsc` can resolve `building_blocks`' dist chunks. Three of its optional peers this app genuinely has no use for (`@sudobility/subscription-components`, `@sudobility/devops-components`, `@sudobility/subscription_lib`) are **not** installed for real — `vite.config.ts` aliases them to local no-op stubs under `src/stubs/` (the "stubs system" pattern, mirrored into `tsconfig.json`'s `paths`; see `../music_app`'s own `src/stubs/`/`vite.config.ts` for the precedent). `EditorPage` and its panels are the one deliberate exception to primitive adoption — see Behaviour notes.

Editor internals (`EditorPage`, `AiPanel`, `TitlePagePanel`, `PageSetupPanel`, `LockingSection`, `DualDialogueToggle`, `RevisionsPanel`, `SceneOmitToggle`, `SnapshotsPanel`, `ConversionReportView`) are **not** converted to `@sudobility/components`/i18n — deeply domain-specific, already heavily e2e-tested, following `writing_ui`'s own conventions. `../music_app` draws the identical line at its own densest screen (the score editor stays hand-rolled-on-Tailwind by explicit, documented choice) — this is the same boundary, not a shortcut.

## Commands

- `bun install`, `bun run dev` (Vite on **5143**, strict; the API's CORS allows this origin), `bun run typecheck` (`bunx tsc --noEmit`), `bunx vitest run` (never `bun test`), `bun run build`.
- `bun run e2e` = `bunx playwright test`. Starts the API (`../screenwriter_api`, `bun run db:init && bun run src/index.ts`, port 18042, `DATABASE_URL=postgres://localhost:5432/screenwriter_test`, `AI_TEST_MODE=1`, `PUBLIC_APP_URL`/`CORS_ORIGINS` = the app origin) and Vite (port 15173) itself; needs local Postgres. `E2E_API_PORT`/`E2E_APP_PORT` override the ports. Screenshots go to `../screenwriter_plans/.superpowers/sdd/frontend-f4-*.png`. First time: `bunx playwright install chromium`.

- Soak (`e2e/soak.e2e.ts`, skipped unless `SOAK=1`): randomized editing sessions hunting the two anomalies in `../screenwriter_plans/.superpowers/sdd/known-gaps.md`. It needs an already-running stack on non-dev ports (API 18342 with `AI_TEST_MODE=1`, `DATABASE_URL=...screenwriter_test`, `PUBLIC_APP_URL`/`CORS_ORIGINS=http://localhost:15373`; Vite 15373 with `VITE_API_URL=http://localhost:18342 VITE_DEV_AUTH=1`). Run: `SOAK=1 SOAK_SEEDS=1,2,3 SOAK_STEPS=60 [SOAK_CHAOS=1] [SOAK_VERBOSE=1] bunx playwright test -c playwright.soak.config.ts -g "soak seed"`. `SOAK_CHAOS` restarts the API on port 18342 mid-run. `SOAK_MECH=1` also enables a probe showing a letter typed on the focused style picker restyles the editor's stale selection.

- AI panel: an **AI** button in the editor top bar opens `components/AiPanel.tsx` on the right (Snapshots and AI share one `panel` state: one at a time). It reads `GET /ai/status` through the lib's `useAi`: `fixture` shows the persistent "Test mode — these results are canned samples, not real AI output" banner, `unavailable` explains AI is not configured and offers no buttons. Review = coverage report (scene notes call the Navigator's `jumpTo`); Polish = current scene (`useEditorSelection` + `model.sceneOf`) with before/after word diffs (`util/diff.ts`, hand-written LCS), Accept selected / Accept all / Reject, stale suggestions marked and explained. `e2e/ai.e2e.ts` covers it (screenshots `frontend-f7-*.png`). The unavailable state is tested with `/ai/status` intercepted: a real API without `AI_TEST_MODE` cannot authenticate the dev login.

## Auth

Real Firebase Google sign-in **and** the dev email-only bypass are both live, side by side on `LoginPage` — not one replacing the other. Both the app's Firebase web config (`.env`'s `VITE_FIREBASE_*`, project `screenwriter-d2c86`) and the API's Firebase Admin credentials are already configured; nothing server-side needed to change.

- `VITE_DEV_AUTH=1` shows the dev email-only form, backed by the lib's `DevAuthPort` (persisted in `localStorage` key `screenwriter.devEmail`; sign-out clears it). Token = `dev:<uid>:<email>`, uid = hash of the email, accepted by the API only with `AI_TEST_MODE=1` (REST bearer and the sync socket's `auth` frame). This is what all 12 e2e specs use (`getByLabel("Dev login (email, no password)")`), so it's kept rather than replaced — unlike `../music_app`'s own `VITE_E2E=1` shim, this app's dev bypass is a real, already-working mechanism the API itself supports.
- Google sign-in uses `firebase/auth` directly (`initializeApp`/`getAuth`/`signInWithPopup`+`GoogleAuthProvider`), not `@sudobility/auth_lib`'s `getFirebaseAuth()` — `../music_app` makes the same choice for its own Firebase calls.
- `src/auth/backend.ts`'s `unifiedAuthBackend()` composes both into one `AuthBackend` (whichever last signed in becomes "active" for `getToken`/`signOut`); `authBackendAsPort()` adapts that backend to `screenwriter_lib`'s `AuthPort` (`currentUser`/`signIn`/`signOut`/`getToken`/`onChange`) so `createScreenwriter()` — a synchronous composition-root call in `services.ts`, before React even renders — has the concrete object it requires. This needed **zero changes to `screenwriter_lib`**: its own docs already describe this exact seam ("the app implements it... the lib never imports an auth SDK"), and `DevAuthPort` was already the only concrete implementation living there.
- `src/app/AuthContext.tsx` is a separate, app-owned React context (`useAuth()`) subscribing to the *same* backend instance `services.ts` built — this is what all UI (routing gate, `ProtectedRoute`, the topbar's `AuthActionAdapter`, `LoginPage`) reads, not `@sudobility/screenwriter_lib`'s own re-exported `useAuth()` (still used internally by the lib's `useProjects()`/`useTemplates()`, unaffected).
- `LoginPage` uses `building_blocks`' actual `LoginPage` component (matching `../music_app`'s real login screen exactly), not a hand-composed alternative — an earlier version of this file said otherwise; that approach was tried and rejected because it doesn't look the same as the shared component. The component always renders a password field (no prop removes it, and it's native-`required`), even though this app has no password concept at all: `onEmailSignIn`/`onEmailSignUp` both call `devSignIn(email)`, ignoring the password value, and the field must still be filled with *something* or the browser's own validation silently blocks submission with no visible error (a real, easy-to-miss trap). Two text overrides only: `emailLabel` (e2e's `getByLabel("Dev login (email, no password)")` depends on it) and `signInWithGoogle: "Continue with Google"` (the component's own default, "Sign in with Google", contains "Sign in" as a substring, making every e2e spec's `getByRole("button", { name: "Sign in" })` ambiguous — `music_app` overrides the same text for the same reason). e2e specs also add `{ exact: true }` to the Password/Sign-in selectors for the same substring-collision reason.

## Local packages: aliases and dedupe (important)

`vite.config.ts` aliases `@sudobility/screenwriter_lib|screenwriter_client|screenwriter_types|writing_ui|writing_core` to the sibling repos' `src/index.ts`, and `yjs`/`lib0` to `../writing_core/node_modules/...` (`yjs/dist/yjs.mjs`: ONE Yjs instance). It also aliases `@sudobility/writing_formats/fountain-classify` (a stable, dependency-free subpath `writing_ui`'s paste classifier imports) straight to `../writing_formats/src/fountain/classify.ts` — this one is a real npm dependency of `writing_ui` itself (not this app), so this alias exists purely so bundling `writing_ui`'s aliased-to-source code doesn't fall through to this app's own (nonexistent) `node_modules/@sudobility/writing_formats`. It also aliases `@sudobility/components/master-detail-layout` straight to `../mail_box_components/src/layout/MasterDetailLayout.tsx` (source repo for `@sudobility/components`): `MasterDetailLayout`/`MasterListItem` are wired into that repo's own barrel but not yet in the published dist this app otherwise depends on for everything else — a narrow, one-file alias, not a whole-package one (`@sudobility/components` is used everywhere here; aliasing all of it to raw source would be a much bigger, riskier change for one missing component). No safe npm fallback exists yet (nothing publishes this component at all, unlike `fountain-classify`'s real fallback); acceptable since this app has no CI of its own and always runs with `mail_box_components` checked out. `tsconfig.json` `paths` mirror it (two-entry `yjs` mapping: extensionless `dist/yjs` first, then the directory for types). Keep the two in sync. `resolve.dedupe: ['yjs','lib0','react','react-dom','@tanstack/react-query','zustand']` is required: the siblings have their own `node_modules`, and the client's hooks (react-query, react) and the lib's stores (zustand) would otherwise load a second copy (broken hooks/context). `server.fs.allow` includes the parent directory so Vite can serve the siblings. `optimizeDeps.exclude` keeps yjs/lib0 out of the pre-bundler for the same reason. The tsconfig also maps `react`, `react-dom`, `zustand`, `@tanstack/react-query` to this app's `node_modules` so types are one copy.

## Behaviour notes

- DashboardPage's project/document rows (`data-testid="project-row"`/`"document-row"`) navigate on a click anywhere in the row, not just the title: an `absolute inset-0` `<Link aria-label={name}>` (no visible text of its own) is the FIRST child, covering the whole `relative`-positioned `<li>`; the title/meta stay plain text. Positioned descendants paint above static ones regardless of DOM order, so this stretched link sits above the plain-text spans automatically — the Trash/Restore `<button>` needs its own `relative z-10` to win back its own clicks. Reuse this pattern for any future list row that should be fully clickable.
- `NewDocumentForm` (DashboardPage's project view): the Kind/Template fields use `@sudobility/components`' `Select`/`SelectTrigger`/`SelectContent`/`SelectItem`/`SelectValue` (per an explicit user requirement — "use Select from mail_box_components"), not native `<select>`s — so e2e specs that need a specific template (not just the auto-selected default) must open it and click the option (`await page.getByLabel("Template").click(); await page.getByRole("option", { name: template, exact: true }).click();`), not `page.getByLabel("Template").selectOption(...)` (a real regression this caused in `columns.e2e.ts`, fixed at the same time). Likewise, checking a template got auto-selected reads the trigger's displayed text (`not.toHaveText("Template")`, its own placeholder), not `.toHaveValue()` (`SelectTrigger` isn't a form-associated element with a DOM `value`, unlike a native `<select>`) — `e2e/app.e2e.ts` had the same fix. The Title input, both `SelectTrigger`s, and the "Create document" button all share a fixed `h-9` height (`fieldClass`/`primaryField`) — per the same request, matching `SelectTrigger`'s own built-in height rather than fighting it with custom padding, since the previous native `<select>`s and the input each had their own slightly different padding/font-size.
- The editor route renders `ScriptEditor` + `ElementStylePicker` from `writing_ui`. `useDocumentSession` opens the session (offline copy first, then sync). Rebase: the lib emits `rebased`; `EditorPage` shows a banner ("Document replaced by snapshot", plus a preserved-locally note if `lostLocalEdits`). The session object is stable across a rebase, the model inside it is replaced; the editor re-reads `host.model` on `subscribe(null)`.
- `EditorPage` is keyed by document id so a fork (navigation to `/d/<new>`) remounts cleanly.
- Snapshots panel uses the session's methods directly (`listSnapshots`, `createSnapshot`, `openSnapshot`, `forkSnapshot`, `listVersions`); Open and Fork use inline confirm/title steps, not `window.confirm/prompt`.
- Status label: `connecting`/`disconnected|error` -> Offline; `state: synced` -> Synced; anything else Syncing.
- **Editor sidebar** (`EditorSidebar.tsx`, `EntityDetailView.tsx`): a persistent, hierarchical master/detail sidebar (Storyist's "Project view" shape, per an explicit user request — `@sudobility/components`' `MasterDetailLayout`/`MasterListItem`, referred to as "from building_blocks" but actually defined in `@sudobility/components`, which `building_blocks`' own `GlobalSettingsPage` composes internally without re-exporting), replacing the old toggle-able Navigator sidebar and the old **Catalog** flyout panel entirely — no more **Scenes** toggle, no more **Catalog** button.
  - **Script Structure**: the existing `Navigator` (`writing_ui`), unchanged — drag-reorder, synopsis editing, omit all still work exactly as before.
  - **Catalog**: every `EntityKind` (`ENTITY_KINDS` — character, location, prop, vehicle, wardrobe, ... all 24) that has an entity, plus Character/Location always (the two the script can harvest), each an expand/collapse group of `MasterListItem` rows — entirely from the live document (`host.model.entities()`/`.entity()`/`.occurrences()`, `entity.*` commands), no API call, like `RevisionsPanel`/`LockingSection`, unlike `AiPanel`/`ImportScript`. Harvesting (`entity.rebuild`) only runs once on mount, not on every edit, so a **Refresh** button (next to the Catalog heading) re-scans by hand. Every other kind only ever exists once created by hand, via a kind's own "+" (inline name field) or "+ Add other kind" (a `Select`/`SelectTrigger`/`SelectContent`/`SelectItem` kind picker — used here specifically because the user asked for it "for any kind of popup select"). Out of scope for now: merge, variants (age/version), tag categories, worksheets, kind-specific custom fields.
  - **Selecting an entity is a real master/detail selection**: `EditorPage` shows `EntityDetailView` (name/rename, kind + scene count, aliases, description, "Appears in" occurrences that jump back into the script via the same mechanism `Navigator`/`AiPanel` use, delete with the existing force-confirm flow) in place of the script editor — not a toggle, not a separate panel. Selecting a scene (`Navigator`'s `onJumpTo`) clears the entity selection, snapping back to the editor. Since `EditorPage`'s one `MasterDetailLayout` instance is passed `detailMaxWidth={0}` (the script editor needs full bleed), `EntityDetailView` constrains and pads itself instead (`max-w-5xl mx-auto p-6`, matching `ScreenContainer`'s own `"5xl"` convention) rather than relying on the layout's own `detailMaxWidth`/`detailPadding` props.
  - **Character skeletons and life stages** (`util/character-skeleton.ts`, `components/CharacterSkeletonEditor.tsx`), per an explicit user requirement: a `character`-kind entity's "Description" is replaced by a structured worksheet (Physical/Social/Psychological — Egri's three-dimensional-character bone structure) instead of a plain-text field. Only Age is required; every other field (~30 total) is hidden until added, so a fresh character doesn't show thirty empty inputs — one click each, via a per-section row of "+ {label}" chip buttons (`AddFieldChips`), not a `Select` menu to open first: that was the original design, but "open the menu, then pick" was flagged as two clicks to reveal one input. A non-required field also has its own "×" clear button inside the field (not a separate button beside it — a familiar clearable-input affordance): clears the stored value, so it doesn't reappear on its own next time (the visible-field seeding is driven by "has a non-empty stored value"), and hides the input; Age has none, it can't be removed. **No `writing_core`/`screenwriter_lib` schema or command changes were needed**: `EntityJSON.attributes` is already a generic, per-entity `Record<string, JsonValue>` bag with a stable regex-checked key format, round-tripped as plain JS by the existing `entity.update` command for any entity kind — the skeleton lives at `attributes["character.skeleton"]`, stages at `attributes["character.stages"]` (an array of `{id, skeleton}`).
    - A character normally has no stages: it's a plain leaf in the Catalog tree, and its own skeleton is edited directly. `EntityDetailView`'s `DetailFrame` gives every return a fixed three-region layout — a genuinely, independently scrollable middle (the skeleton form) and a "+ Add Age" button pinned in normal flow at the bottom (`footer`, present only on a `character`-kind entity), *not* `position: sticky` (that was the original design, but sticky only pins once scrolled *past* its natural position — on a short, mostly-empty skeleton it just sat right after the last field instead of staying at the bottom of the pane). First click: the un-staged skeleton becomes stage 1 (keeping its current age/fields), a second, blank stage is appended and auto-selected, and the character becomes an expandable branch in the sidebar (`EditorSidebar`) — nested `MasterListItem` rows labeled by each stage's age, or "New" until one is filled in (typing the age and blurring updates that row's label live, off the same `useModelTick` re-render everything else in the sidebar already uses). Later clicks just append one more blank stage.
    - Stages are **not** separate entities (unlike locations' `parentId` nesting) — deliberately: two different characters both having a same-aged stage (e.g. two "50"s) would collide under `entity.create`'s global per-kind name dedup (`findByKey`) if each stage were its own top-level `character` entity. An embedded array on the parent avoids that class of bug entirely, and needs no `occurrences()`/tag-linkage story either (a scene doesn't reference a specific life stage, only the character overall) — name/"Appears in"/delete stay at the character level; a selected stage shows only its own skeleton plus a simple (non-force) "Delete this stage" confirm.
    - **Aliases** (`entity.aliases`, a real entity-level thing, not a skeleton field) render *inside* the Social section of the un-staged skeleton (`CharacterSkeletonEditor`'s `socialExtra` prop — per an explicit user requirement, "make Aliases part of social skeleton"), not as a separate section above it — but only there: a per-stage skeleton doesn't get `socialExtra` (aliases don't vary per life stage), and a staged character's "Life stages" list view (no skeleton on screen at all) keeps Aliases as its own standalone section, so it's never simply unreachable once a character gains its first stage.
    - Selection is a compound `(entityId, stageId | null)` throughout (`EditorPage`'s `selectEntity`/`selectedStageId`, `EditorSidebar`'s `onSelectEntity(entityId, stageId?)`, `EntityDetailView`'s `stageId`/`onSelectStage`) — a character with stages shows a "Life stages" list (jumping to any one) instead of a single skeleton when the character itself (not a stage) is selected.
    - `e2e/catalog.e2e.ts` covers the whole flow: filling Age, adding an optional field, Add Age migrating the existing skeleton into stage 1, the new stage's label updating live as its age is typed, switching between stages, and deleting one.
  - **Aliases are Character-only**, not a generic thing every kind gets — it was never a deliberate choice for the other ~22 kinds, just the fallback they all inherited by default from one shared `!isCharacter` branch; per an explicit user question ("why do you have Aliases for everything in Catalog?") it's now scoped down to the one kind where "known by other names" is a real, common concept (nicknames).
  - **Locations** also get a **Setting** section with two toggle buttons, "Interior (INT)"/"Exterior (EXT)" (`entity.fields.setting`, already a real typed field on `LocationFields` in `writing_core` — `int`/`ext`/`intExt`/`null`, though only the first two are offered here since that's all that was asked for; **no `writing_core` changes needed**, `entity.update`'s existing `patch.fields` merge already validates and writes it for any entity kind). Clicking the already-selected button clears it back to unset.
  - **Built-in Story items** (`util/story-info.ts`), per an explicit user requirement — "under Catalog, also show... Plot (one main plot, 0..N subplots), theme, tagline, synopsis": a pinned "Story" group sits above the kind-groups in the Catalog tree, not derived from `ENTITY_KINDS`/harvesting like everything else there. None of `writing_core`'s document-level collections fit (a `Plot`/subplot is conceptually close to the schema's own already-declared-but-never-implemented `storylines`/`StorylineJSON`, but that has no reader on `DocumentModel` and no commands at all — building those from scratch was a bigger lift than this needed) and `ENTITY_KINDS` is a closed enum shared with `screenwriter_api`'s own copy of the same schema package, so extending it risks a real version skew this app's own `writing_core`-aliased-to-source setup doesn't share with the API. So: the same technique as character skeletons — one hidden, auto-provisioned `misc`-kind entity (`ensureStoryEntity`, called once per `EditorSidebar` mount alongside the existing `entity.rebuild`; idempotent) holds Theme/Tagline/Synopsis/main-plot as plain attribute strings and subplots as an attributes array (`{id, name, text}[]`), filtered out of the normal per-kind Catalog listing by a reserved attribute marker so it never shows twice. `EditorSidebar`'s `onSelectEntity`'s `stageId` slot is repurposed as the selected story item's key (`"theme" | "tagline" | "synopsis" | "plot" | "subplot:<id>"`) rather than a character life stage; `EntityDetailView` special-cases this entity entirely (no name/aliases/occurrences/delete — those don't apply to a hidden container record), rendering just the selected item's field(s), with a "+ Add subplot" footer button (same fixed-footer `DetailFrame` as "+ Add Age") while viewing the main plot or any subplot, and a simple (non-force) "Delete this subplot" confirm. `e2e/catalog.e2e.ts` covers filling each item, adding/renaming/deleting a subplot, and that values persist across navigating away and back.
  - **Structured AI actions** (`POST /ai/{action}` in `screenwriter_api`, synchronous; client methods `generateCharacterSkeleton`/`generateScript`/`polishCharacterDialogue`/`polishScene` in `screenwriter_client`): four features, each integrated where the writer already is. Shared plumbing: `hooks/useAiActions.tsx` (server availability via `useAiStatus`, the **AI consent gate**, one busy/error state, the credit balance; `run(call)` asks for consent first when it has not been given, and also handles the API's `AI_CONSENT_REQUIRED` for a stale cache) and `components/AiNotices.tsx` (test-mode banner, "not configured", the consent notice, error, credits). Errors are turned into plain language (`explainAiError`); a failed or invalid call is never charged, and the panel says so.
    - **Character skeleton from a description** (`GenerateSkeletonBox`, in `EntityDetailView` above the skeleton form, for a character's own skeleton and for each life stage): a free-form paragraph -> structured skeleton, **merged onto the skeleton filling blank fields only** (`mergeSkeleton` — never overwrites what the writer wrote, so regenerating is safe; the result line lists which fields were filled). The skeleton form is uncontrolled, so applying bumps a `skeletonVersion` key to remount it with the new values.
    - **Polish a character's dialogue** (`PolishDialogueSection`, in the character view, before "Appears in"): sends that character's lines (all, or one scene they speak in; max 100 at once) with their skeleton (a staged character picks "Write as" which age) and an intensity; shows every changed line as a before/after word diff (`WordDiff`, extracted from `AiPanel`) with a checkbox each; **nothing is applied until the writer applies the ticked lines** (`applyLineEdits` -> `text.replaceRange`), and a line edited since is skipped, never overwritten.
    - **Generate a script from a story** (`GenerateScriptSection`, in the AI panel): preview of scenes with structured headings, then "Insert into script" (`insertScript`: an empty new document's starter element is reused for the first heading, otherwise appended after the last element; every element is an ordinary `element.insert`, so it is undoable and syncs; styles are looked up by role, so templates lacking a role skip those elements and say so) and the editor jumps to the first inserted element.
    - **Polish the current scene with the characters' skeletons** (`PolishSceneSection`, in the AI panel, distinct from the existing job-based "Polish dialogue"): sends the scene body plus a skeleton for every character who speaks in it (`speakersIn`; a character with no skeleton is sent as age "unspecified" and flagged "no skeleton yet"; one with life stages picks which age). The result is a **freely rewritten** element list shown before/after side by side; "Replace scene" (`replaceSceneBody`) inserts the new elements after the old body and deletes the old body as one `text.deleteRange` starting at the heading's end, so the heading, its scene number and neighbouring scenes are untouched, and it **refuses if the scene changed since the AI saw it**. A scene with elements the API has no type for (notes, shots) disables the button — replacing it would lose them.
    - Reading/writing helpers live in `util/ai-script.ts` and are unit-tested against a real headless document (`tests/ai-script.test.ts`, using `writing_core`'s `commandHarness`); `e2e/ai-actions.e2e.ts` covers all four flows through the UI (a fresh user per test, since consent is per user). The existing AI panel's Review/Polish now shows the same consent notice (it used to show a generic error, and `e2e/ai.e2e.ts` had been failing on it).
  - **The editing bar** (`data-testid="editing-bar"`, per an explicit user requirement — "some buttons only make sense with the script editor... move those to an editing bar"): view-mode-specific tools (`ElementStylePicker`/`DualDialogueToggle`/`SceneOmitToggle` for Edit view, Print for Pages view) live in their own bar between the nav header and the content area, not mixed into the main header with document-level chrome (back link, title, view tabs, `RevisionIndicator`, `ExportMenu`, page count, sync status, Title page/Page setup/Revisions/AI/Snapshots). Hidden entirely whenever the sidebar's Catalog selection replaces the content area with `EntityDetailView` — none of these tools act on an entity.
  - `EditorPage.tsx` wraps the sidebar/detail area in exactly one, permanently-mounted `MasterDetailLayout` — `masterContent` is always `EditorSidebar`, `detailContent` is `EntityDetailView` when an entity is selected, the script editor otherwise. This used to need a workaround (two different tree structures, `EditorSidebar`'s expand state lifted to `EditorPage` to survive remounting between them) because `MasterDetailLayout` always mounted a second, CSS-hidden (`md:hidden`) copy of whatever it was given — harmless for the sidebar and `EntityDetailView`, but a real bug for `ScriptEditor` (confirmed directly: two live `data-testid="script-editor"` elements). **Fixed upstream**, in `mail_box_components`'s `MasterDetailLayout.tsx` itself (`useIsDesktop`, a real `matchMedia`-driven hook, replaces the old CSS-only `hidden md:flex`/`md:hidden` split) — the desktop/mobile choice is JS-computed now, so exactly one copy of each pane ever mounts, and the workaround was removed once that landed (confirmed with a direct DOM count: exactly one `script-editor`, one `editor-sidebar`, one `aside`). `EditorSidebar` owns its own expand/collapse state again.
  - `MasterDetailLayout`'s own master panel is a plain `<aside>` with no prop to reach it directly, unlike the old Navigator sidebar (which was `print:hidden` on itself) — `src/index.css` has a small, targeted `@media print` rule instead (`[data-testid="editor-split"] aside { display: none !important; }`).
  - `e2e/catalog.e2e.ts` covers harvesting, the hierarchical browse/select/detail flow, jumping back to the script, and a manual (non-harvestable) kind.

## Gotchas

- `@sudobility/components`' `MasterDetailLayout` used to always mount BOTH a desktop and a CSS-hidden (`md:hidden`) mobile copy of `masterContent`/`detailContent` — real DOM elements, not conditionally rendered, just responsive-hidden. Harmless for cheap, non-"live" content, but a genuine bug for anything with live, stateful DOM management (confirmed directly here: putting `ScriptEditor` in `detailContent` produced two real, simultaneously-mounted contenteditable instances). **Fixed upstream** in `mail_box_components/src/layout/MasterDetailLayout.tsx` (a real `matchMedia`-driven `useIsDesktop` hook now decides desktop vs. mobile in JS, so exactly one of each pane mounts; the mobile nav↔content slide transition is untouched) — this app picks the fix up immediately since `vite.config.ts` aliases `@sudobility/components/master-detail-layout` straight to that source file. Still worth knowing if working directly in that component: the fix required the same care in its own test suite (jsdom has no `matchMedia` at all; a naive polyfill that defaults unrecognized queries like `prefers-reduced-motion` to `matches: true` will silently disable the slide animation — default unrecognized queries to `false`).
- The API must expose `X-Epoch`/`X-State-Vector` via CORS (fixed in screenwriter_api 6818de6); without it a browser reads every state epoch as 0 and rebase never completes.
- API `.env` autoloads the DEV database; always pass `DATABASE_URL` explicitly when starting it for tests.
- `writing_core` has stray compiled `.js/.d.ts` next to its `.ts` sources; harmless here.
- A relative `<Navigate to="404">` from the `*` wildcard route does NOT resolve to a sibling "404" segment — it repeatedly appends onto the unmatched path instead (`/en/x` -> `/en/x/404` -> `.../404/404` -> ... infinite loop, surfaces as "Maximum update depth exceeded"). Use an absolute, lang-prefixed target (`App.tsx`'s `CatchAll`).
- `@sudobility/components`' `FormModal`/`Dropdown` have no `data-testid` seam on their container or action buttons (unlike the retired hand-rolled `Modal.tsx`) — e2e specs select them by `getByRole("dialog")`/`getByRole("button", {name: ...})`/visible text instead; watch for two same-named buttons at once (a dialog's action vs. the trigger behind it) and scope the locator to the dialog when that happens.
- `ScreenContainer`'s `AppPageLayout` **must** get an explicit `page={{ layoutMode: "full", maxWidth: "5xl", contentClassName: "w-full min-w-0" }}` (all three — matches `music_app`'s own `page` config exactly). Missing any one of them lets the content wrapper's cross-axis size resolve via shrink-to-fit instead of stretching to the maxWidth-capped width: it collapses to whatever its own content's intrinsic width happens to be — anywhere from ~32px (a `Section`'s full-bleed children, the negative-margin `calc(50% - 50vw)` trick, pulling the calculation one way) to a few hundred px (a plain page with no wide element, no bleed involved at all — this isn't only the bleed-vs-overflow interaction it first looked like). `music_app`'s own `ScreenContainer.tsx` documents the identical failure ("the page's cards started at 32px"). Verify visually (screenshot, or measure `getBoundingClientRect().width` directly), don't just check for console errors — a collapsed-width bug produces zero console/JS errors.
- The theme is `retroTheme` (`configureTheme()`/`generateThemeCSS()` in `services.ts`, imported from `@sudobility/design/themes` — other options include `defaultTheme`, `swissTheme`, `navyTheme`, `neoBrutalismTheme`, `glassmorphismTheme`, `cyberpunkTheme`, `vaporwaveTheme`, `y2kTheme`, `linearTheme`, `notionTheme`, and more app-family-specific ones). Every `@sudobility/components`/`building_blocks` component with a `variant="primary"`/`colorVariant="primary"` (the default throughout this app, never overridden) reads its actual color/type treatment from whichever theme is active, with no other code change — swapping the one `configureTheme(...)`/`generateThemeCSS(...)` pair restyles the whole app at once.
- Any topbar/auth control (`AuthActionAdapter`'s signed-out button, etc.) renders through `@sudobility/components`' `Button`, never a hand-rolled `<button className="...">` — a hand-rolled button bypasses the active theme entirely and looks wrong regardless of which theme is configured (this was a real bug here: a plain black button next to theme-red buttons everywhere else).
- Playwright's `getByRole`/`getByLabel` string matching is a case-insensitive **substring** match, not exact, unless `{ exact: true }` is passed — "Sign in" matches "Sign in with Google" too, "Password" matches "Dev login (email, no password)" too. Any two labels/button names sharing a common word need `exact: true` on both sides or the selector is ambiguous.
- `t(key, { returnObjects: true })` can crash the page on a cold load: `i18n.ts`'s `i18next-http-backend` fetches translations asynchronously and `react: { useSuspense: false }` means React renders before that fetch resolves, so `t()` returns the raw key **string** on the first render — calling `.map()` on it throws (`items.map is not a function`), caught by `ErrorBoundary` as "Something went wrong". Found via `content-pages.e2e.ts` hitting this on a fresh `/en/contact` navigation. Use `util/i18n-array.ts`'s `translatedArray(t, key)` (an `Array.isArray` guard, falls back to `[]` for that one render) instead of casting `t(...)` directly, anywhere a translated array is rendered with `.map`.
